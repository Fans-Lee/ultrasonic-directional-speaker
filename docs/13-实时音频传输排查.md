# 实时音频传输排查

> 版本：v1.1
> 日期：2026-09-13

适用现象：普通音箱播放量化后的 WAV 清楚，转换为内置 `audio_data.h` 后阵列也能清楚播放，但实时麦克风流不清楚。

## 已定位的实现差异与问题

1. 内置播放在固件复位后的默认值是 `DSB + LOUD + BOOST`，旧版实时麦克风流曾固定请求 `DSB + RAW + STANDARD`；当前实时链路由配置/UI选择模式，项目配置已改为 `DSB + LOUD + BOOST`。转换工具还会去直流、归一化和淡入淡出。因而必须用同样的 PCM 字节和同样的模式比较，才能隔离传输因素。启动过实时流后，固件的模式可能已经改变，内置对照应明确指定模式。
2. 固件只缓存最近一条可靠命令的 ACK。旧电脑端连续发送 `STREAM_START` 和 `SET_MUTE` 时，如果启动 ACK 丢失，后一个 ACK 会覆盖缓存；随后重试启动命令会清空音频缓冲。这已在模拟串口测试中复现，修复后同一启动命令只执行一次。电脑端现按顺序等待可靠命令 ACK，普通音频帧不要求 ACK。
3. 本机 Arduino-ESP32 3.3.10 的 HardwareSerial 默认接收环形缓冲只有 256 字节，常规音频帧约 185 字节，主机积压时可能连续发送多个包。固件现将 UART RX 缓冲增至 4096 字节；这是缓解突发/调度阻塞的措施，不代表已证明现场发生 UART 溢出。该缓冲与 2048 样本的解码后音频缓冲不同，USB CDC 不应用此 UART 设置。
4. 旧命令行未显示 CRC、音频序号缺口和 GPTimer 跳样；现已补齐，视觉界面的串口详情也会显示 under/over/crc/gap/skip/host_drop。

## 用内置 PCM 做串口对照

在仓库根目录运行，以下 `COM5` 替换为实际 ESP32 串口。先退出其他占用串口的程序，包括视觉界面和 Arduino 串口监视器。

不接触设备，仅检查文件格式和样本哈希：

```powershell
uv run python .\utils\audio_stream_probe.py --inspect-only
```

默认读取 `src/full_size/src/data/audio_data.h`，可用 `--audio-header` 覆盖。工具读取十进制 `kAudioSamples` 数组，**不重新归一化、不经过麦克风 DSP**；每包最多 160 样本，以 8 kHz 速率发送，默认重复 3 次。末尾追加超过一整个设备音频缓冲的静音，避免停止命令截断原音频；这个静音尾段不是音频源的一部分。

先明确内置对照：在固件未建立二进制会话时，用串口字母命令选择 `D R N P`（DSB、RAW、STANDARD、播放一次）。已经建立二进制会话时，需要退出电脑串口程序并复位固件才能再使用字母命令。随后关闭串口监视器，运行匹配的串口播放：

```powershell
uv run python .\utils\audio_stream_probe.py --serial-port COM5 --processing raw --drive standard --log-jsonl .\output\probe_raw_standard.jsonl
```

再比较内置 `D E B P` 与下列同模式串口播放：

```powershell
uv run python .\utils\audio_stream_probe.py --serial-port COM5 --processing loud --drive boost --log-jsonl .\output\probe_loud_boost.jsonl
```

LOUD/BOOST 是与内置默认值对齐的对照条件；对照命令不会改写实时链路配置。没有特别改过的内置播放通常是 DSB；只有对照明确使用 SRAM 时，才加 `--modulation sram`。

如有 under 增长，可在同一模式下再比较 120 ms 预缓冲：

```powershell
uv run python .\utils\audio_stream_probe.py --serial-port COM5 --processing loud --drive boost --prebuffer-ms 120 --log-jsonl .\output\probe_prebuffer120.jsonl
```

较大的预缓冲只能缓解有限抖动，不能修复持续丢包、CRC 错误和 GPTimer 跳样。工具遇到断连、状态过期、设备异常静音或从未报告 PLAYING 时会报告失败并停止；不会把“电脑发完字节”当成设备正常播放的证明。

## 麦克风实时流日志

```powershell
uv run python .\utils\mic_stream_cli.py --serial-port COM5 --log-jsonl .\output\mic_stream_diagnostic.jsonl
```

这条命令只启动麦克风，不启动视觉和云台跟踪。日志每秒保存一次完整状态，文件含相对时间，可比较计数增量。处理与驱动模式读取 `configs/vision_gimbal.toml`；当前整机配置为 `LOUD + BOOST`，应使用相同模式的文件流比较。

立体声混音使用相同诊断入口：

```powershell
uv run python .\utils\mic_stream_cli.py --serial-port COM5 --source stereo_mix --log-jsonl .\output\stereo_mix_diagnostic.jsonl
```

物理扬声器静音后仍应采到电脑声音的诊断入口：

```powershell
uv run python .\utils\mic_stream_cli.py --serial-port COM5 --source system_loopback --log-jsonl .\output\system_loopback_diagnostic.jsonl
```

进程回环在真实数字静音持续1秒后会主动停止ESP32流，此时 `IDLE/MUTED` 或界面的“等待电脑声音”是正常结果；开始播放内容后应重新进入 `PREFILL`，随后变为 `PLAYING/False`。Windows主音量静音不应触发这个门控。

## 日志判读

| 终端字段 | 含义与判断 |
|---|---|
| `state / muted` | 正常持续播放应为 `PLAYING / False`。只看 connected 不够；超时后设备可能保持 MUTED 而电脑仍继续发数据。 |
| `buffer` | 解码后的 PCM 缓冲，容量 2048 样本。持续贴近 0 易欠载，持续贴近满值易溢出。 |
| `under` | 设备没样本可播；现有固件会关闭 PWM、重新预缓冲，因此会产生断续。 |
| `over` | 设备 PCM 环形缓冲满，拒收新包。不是 UART RX 缓冲溢出的直接计数。 |
| `crc` | 固件解码错误总数，包括 COBS、长度、标识和 CRC 错误，不能全部解释成电气位错误。 |
| `gap` | 有效音频包的样本序号不连续，可能来自主机丢包或途中坏帧。当前固件没有补齐缺失样本。 |
| `skip` | GPTimer 积压而跳过的样本数。若它增长而 crc/gap 为 0，优先检查播放调度和任务阻塞。 |
| `host_drop` | 电脑发送队列满后丢弃旧包。建连等待期间可以增加，重点看稳定播放时是否继续增长。 |
| `capture_drop` | 当前实时音源的采集队列满后丢块；文件诊断工具不使用实时采集。 |
| `rx_error` | 电脑接收固件状态/ACK 时的帧解码错误。建连的未分帧启动日志也可能增加该数，需看稳定期增量。 |
| `tx_samples / tx_queue` | 主机已交给串口驱动的样本累计数及本地待发送包数，不等于设备实际播放数。 |
| `audio_age_ms` | 固件距最近一次有效 AUDIO_DATA 的时间；默认超过 100 ms 会使设备静音。 |
| `status_age_ms` | 电脑距最近有效 STATUS 的时间；None 表示从未收到，持续增大说明正在看旧状态。 |
| `late_max_ms` | 仅文件诊断工具显示，电脑发送循环最大调度迟到时间；不是物理 UART 延迟的测量。 |
| `clip` | PCM_U8 量化输入越界计数，不能代替前级压缩器/限幅器触顶比例。 |

应比较稳定播放 10 秒内的计数增量，保留文件头记录的 PCM 哈希、模式与预缓冲参数。

| 对照结果 | 下一步 |
|---|---|
| 同模式内置清楚、文件串口流差，crc/gap 增长 | 查 UART 接收、主机丢包、线缆/连接与固件串口任务是否及时读取。比较原固件与扩大 RX 缓冲后的固件。 |
| 同模式文件流差，只有 skip 增长 | 查 GPTimer 到播放任务的调度和实时流特有负载，增加音频预缓冲不能解决这类跳样。 |
| 文件流 under 增长，120 ms 预缓冲后减少 | 有调度/传输抖动；进一步结合 host_drop、late_max_ms 和 gap 定位来源。 |
| 文件流清楚、同模式麦克风流差 | 查实时采集、电脑处理开销、时钟控制、实际信号电平；比较只开麦克风与同时开视觉。 |
| RAW 两种路径都弱或含混，LOUD/BOOST 两种都清楚，错误不增长 | 首要差异是电平/处理模式，不能认定传输损坏。 |
| 同字节、同模式仍不同且全部计数稳定 | 零计数仍不能排除亚样本 PWM 抖动或固件版本差异，下一步测 GPIO 更新间隔并核对板上程序。 |

## 验证范围

仓库中的自动测试覆盖：

- COBS、CRC、帧分片和噪声恢复；
- STREAM_START、ACK 重试和过期 ACK 隔离；
- 状态帧更新时间；
- 云台有符号百分之一度编码；
- 诊断工具发送 PCM 字节和处理模式的一致性；
- 音频预处理、重采样、队列、活动门、录音和频谱；
- 当前视觉、控制、UI 和可选声场服务。

从仓库根目录运行：

```powershell
uv sync --locked --python 3.11
uv run python -m pytest -q
uv run python -m compileall -q src utils
```

测试数量会随实现变化，不在文档中固定写死。pytest 只收集 `tests/`，不依赖 `src/cv_test_deprecated` 的导入副作用。

自动测试仍不能覆盖真实 UART 中断、USB 转串口调度、双核竞争、GPTimer/LEDC 实际更新时间、12 路传播延时、功率温升或声学效果。Arduino 固件必须在锁定的板包版本下另行编译；涉及 UART RX 缓冲或固件状态机的修改必须重新烧录 `src/full_size/full_size.ino`。

历史一次性验证若只存在于被忽略的 `work/` 目录，不应作为其他克隆可复现的仓库证据。需要长期保留的协议桩、脚本和结果应迁入 `tests/` 或受版本控制的证据目录。

最终诊断必须保留实际硬件日志，并记录 Git 提交、固件版本、COM 口、音源、处理模式、运行时长和测量接线。
